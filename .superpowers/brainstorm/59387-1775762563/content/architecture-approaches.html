Architecture Approach — Pick One

How should we structure the FairCheck system? All use the same stack (Next.js + FastAPI + Supabase + Claude API).
The difference is how the pieces connect.

A

Monolith API — Single FastAPI Server

Everything in one Python service. Quote analysis, web search, scraping, LLM calls, user management — all endpoints on one FastAPI server. Next.js frontend calls this single API.

Pros

  • Fastest to build — no inter-service communication
  • Simple deployment (1 backend, 1 frontend)
  • Easy to debug — single process, single log
  • Shared state and caching in-memory

Cons

  • LLM calls block other requests (need careful async)
  • Harder to scale individual bottlenecks
  • Single point of failure
  • Gets messy past ~50 endpoints

Best for: Getting to market fast, iterating quickly, solo/small team

B

Modular Monolith — Domain Routers + Background Workers

One server, but internally organized by domain. FastAPI with separate routers (auto, medical, home, legal). Background workers (Celery/ARQ) handle slow tasks (scraping, LLM calls). Clean internal boundaries without microservice complexity.

Pros

  • Still one deployment, but well-organized
  • Background workers = non-blocking LLM/scrape calls
  • Easy to extract into microservices later if needed
  • Each domain module is independently testable
  • WebSocket support for real-time verdict streaming

Cons

  • Slightly more setup (Redis for task queue)
  • Need to manage worker processes alongside API
  • ~20% more initial code than pure monolith

⭐ RECOMMENDED — Best balance of speed, quality, and future scalability

C

Microservices — Separate Services Per Domain

Each domain is its own service. API Gateway routes to auto-service, medical-service, search-service, etc. Each deploys independently. Full event-driven architecture with message queues.

Pros

  • Maximum scalability — scale hot services independently
  • Team can work on domains in parallel
  • Fault isolation — one service failing doesn't kill others
  • Technology flexibility per service

Cons

  • Massive overhead for a new product — 3-5x slower to build
  • Complex deployment, monitoring, and debugging
  • Network latency between services adds to response time
  • Premature optimization — you don't need this until 100K+ MAU

Best for: Large teams, proven product-market fit, high scale

My recommendation: Option B (Modular Monolith). You get clean domain separation and non-blocking AI calls without microservice pain. When you hit scale, each router + worker pair can be extracted into its own service with minimal refactoring. This is how Shopify, GitHub, and Basecamp scaled to millions.
